# Rules for AI coding assistants

This is an experimental point-cloud corner detector. Preserve numeric behavior unless asked for a numerical change. Read `docs/ARCHITECTURE.md` and the function to be changed before editing.



1. **Keep algorithms separated:** `edge_suppression.py`/`candidate_extraction.py` own dense scoring and 3-D NMS; `validator_pipeline.py` owns shared composition; `cornervins_plane_extraction.py` owns query-local organized AHC, RANSAC/refit, merging, and convex hulls; `corner_2d.py` owns continuous 2-D boundary evidence; `boundary_support.py` owns Gaussian boundary weights; `plane_edge_graph_pipeline.py` owns Hough, finite lines, 3-D restoration, and merging; `refiner.py` owns post-detection robust refinement. Do not merge these layers for convenience.
2. **Centralize all detector visualization:** access screens via `corner_detector/visualization/manager.py`. Add a 2D plot in `visualization/plots.py`, 3D elements in `visualization/view3d.py`, key bindings in `visualization/query_ui.py`. Do not directly create figures/Open3D views from `query_debug.py`, `dense_heatmap.py`, or `runner.py`.
3. **Keep one primary validator path:** `validator_pipeline.run_validator_pipeline` is the canonical plane-cluster → padded boundary/Hough → 3-D graph → refiner entry point. Interactive validator queries and detector NMS seeds must call it instead of copying its stages.
4. **Maintain interface and indexing contracts:** `run_validator_pipeline(points_mm, query_index, cfg, estimator)` receives an index into the supplied 3-D-voxelized `points_mm`; all projection, boundary, Hough, and refiner support IDs must preserve that scene-index space. Click indices from the unvoxelized `PointCloudFrame` are **not** interchangeable. All lengths are mm.
5. **Diagnostics may read but never mutate** stored numerical results. Visual caches can be replaced or cleared without recomputing the algorithm.
6. **Run tests** using `python3 -m unittest discover -s tests -v`; run `python3 -m corner_detector --help`; verify imports. When changing a numeric algorithm, add a test with expected numerical behavior, not only screenshot-based evidence.
7. **Don't claim device tests were performed** unless actual STL GUI/RealSense/Kinect+PCL environment was run. Headless tests cover architecture/UI management only.
8. **Before code changes** specify exactly which files/functions you will modify and what numeric behavior should stay invariant; after changes report tests, regression risks, and any unverified hardware paths.
9. **Ignore archived code:** The `/past/` directory contains outdated implementations kept only for historical reference. Do not read, analyze, modify, import, or use files in `/past/` as a reference for current architecture or numerical behavior unless explicitly instructed. Base all decisions on the active codebase and `docs/ARCHITECTURE.md`.
10. **Keep the methods ledger synchronized:** `docs/PIPELINE_METHODS.md` is the canonical paper-style description of the active detector/validator equations, stage order, units, invariants, result semantics, and limitations. Any change to `dense_heatmap.py`, `edge_suppression.py`, `candidate_extraction.py`, `validator_pipeline.py`, `cornervins_plane_extraction.py`, `plane_projection.py`, `corner_2d.py`, `boundary_support.py`, `plane_edge_graph_pipeline.py`, `refiner.py`, their visualization semantics, or related fields in `settings.py` must update the affected methods text in the same task. Record a dated revision when numerical behavior, pipeline ownership, configuration, or output semantics changes; do not create revision noise for formatting-only edits.
